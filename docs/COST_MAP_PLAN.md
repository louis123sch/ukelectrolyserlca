# Cost map plan — 30 Oct 2026

**Goal.** A cost map that works like the LCA map: one page, read off the code
and generated by it, showing every pound the cost objective charges — which
term it sits in, which number it multiplies, the line of code that made that
number, the numbers that went into it, and **the published document or data
feed each one came from**. Nothing typed by hand, nothing left out, and a build
that refuses to write a map that disagrees with the model.

Status (30 Oct 2026, evening): built. Decisions taken as recommended in §5:
pounds from one solved run (London, 2025, 100 MW IT, least cost, the optimiser
choosing its price list), a separate page sharing the LCA map's readers and
look, the source register in Python, and the grid modules recorded while the
grid-connection sessions were idle (additive only; their uncommitted changes
untouched).

| Step | Where |
|---|---|
| A. Every cost number recorded | `T.cost` in `tech_costs`, `battery`, `h2_capex`, `dc_inputs` (bought hydrogen, the grid coefficients, the import price's parts), `network_charges`, `duos_areas`, `levies`, `connection_cost`. 259 cost steps on the London run. Model unchanged: every `Tech` field in 8 variants, the price series, the network charges and a one-week solve equal before and after |
| B. Source register | `optimisation/source_register.py`: 53 sources (25 written out, 10 connection price lists and 18 DUoS / loss-factor workbooks read off `connection_cost` and `duos_areas`) |
| C. Builder | `scripts/build_cost_map.py` (imports `build_lca_map`'s readers rather than moving them) |
| D. Page | `scripts/cost_map_template.html`, derived from the LCA map's: cost graph tab and a Sources tab |
| E. Checker | `scripts/check_cost_map.py`, `tests/test_cost_map.py` |
| Rule | `docs/LCA_STYLE.md` §1, the cost paragraph |

Not done from the plan: the grid is one chain, not three — its terms already
split it (per MW, per year, winter peak, imports, export). Register entries are
not yet held to a `SOURCES.md` row. Most sources have no public link recorded:
the code and documents only ever recorded the NESO, Elexon and Modo addresses.

## 1. What the LCA map does, and what changes for cost

The LCA map (`scripts/build_lca_map.py`, published at
claude.ai/artifact/NrzMeByK24RpbGosfc5aSE) reads the code three ways
(memory note *lca-map*, the 28 Oct conversation that built it):

| LCA map reading | Cost map equivalent | State today |
|---|---|---|
| 1. The LP's terms: `dc_model.objective_terms` evaluated on symbols, grouped by `dc_model.CHAINS` | The same function's `cost_capital` and `cost_operational` groups, plus the fixed connection charge from `objective_constants` | **Ready.** Already written once in `dc_model`; the cost groups are read the same way |
| 2. How each coefficient is made: every `T.step(...)` recorded while `build_tech` / `build_series` run | Every pound figure recorded the same way | **The blocker.** The carbon side has ~140 recorded steps. The cost side has two (`connection.<option>.cost_per_MW_year` and `cost_fixed_per_year`, `dc_inputs.py:984`). Every other cost number — `cost_wind`, `cost_batt_e`, `cost_ely`, `cost_tank`, `cost_fc`, `cost_grid_*`, the bought-hydrogen price, the import price series — is computed in plain code (`dc_inputs.py:866-885`) and is invisible to a trace |
| 3. The inventories: every Brightway activity and exchange, scored | **No equivalent.** Replaced by a *source layer*: one box per document or data feed, every number linked to the one it came from | To build |

So the work is mostly step A below — recording the cost numbers where they are
computed — and the map itself is then the same machine pointed at them.

## 2. What the page will show

Same look and behaviour as the LCA map: one box per thing, a shared input drawn
once with lines converging on it, search, a datasheet panel on the right with
"Used by", badges for open gaps only, no illustrative boxes.

Top to bottom:

1. **The study box.** The reference run (proposed: London, 2025, 100 MW IT,
   cost-optimal, the optimiser choosing its own price list) with its total
   £/year and £/MWh served, solved — so each box below can also show *how many
   pounds it contributed in that run*, not only its unit price. (Decision 1.)
2. **Chains.** Wind, solar, battery, electrolyser, hydrogen tank, fuel cell,
   bought hydrogen, unserved load, and the grid split three ways because it is
   most of the bill: *building the connection*, *network charges for having
   it*, *the price of each MWh imported*.
3. **Terms.** Each LP cost term with its expression, e.g. `cost_wind × cap_wind`,
   `cost_grid_triad_per_mw_year × triad_mw`, and with price lists on, one box
   per price list the optimiser could pick, the chosen one marked.
4. **Coefficients.** `coefficient.cost_wind` etc. — value, unit, the code line.
5. **Steps.** How each coefficient is made: capital cost, yearly running cost,
   life, discount rate → yearly repayment factor → £/MW/year. Each with its
   value, unit, file:line, the expression, its inputs, and its grade
   (transcribed / derived / assumed / proxy).
6. **The import price, taken apart.** The half-hourly £/MWh is a sum; each part
   is a box with its yearly mean, min and max in the reference run:
   wholesale price; balancing charge; losses on the way to the site (local line
   loss factor × national loss multiplier); local network charge by time band;
   each policy levy (Renewables Obligation, Feed-in Tariff, Contracts for
   Difference, the Highlands and Islands distribution subsidy (AAHEDC), Nuclear funding, Climate Change Levy,
   Capacity Market in its winter window). The build checks the parts add back
   to the series to 1e-9.
7. **Sources** — see §3.

Assumed numbers get their own colour, so the unsourced ones stand out on the
page at a glance (the 6 % discount rate, the £100,000/MWh value of lost load,
two circuits per connection, the fuel cell and tank prices…).

Variants, as the LCA map does them (a step that differs gets its own box,
labelled): cost case low / high; AE and SOEC electrolysers; grey, blue and
turquoise hydrogen. One area only (London); the other thirteen areas stay with
`scripts/check_connection_chain.py`.

## 3. Sources — the part that has to be right

Today a cost number's source is a free-text string where it exists at all
(`tech_costs.TECHNOLOGIES` carries "Table 3, p.6"; `connection_cost` carries
it in its docstring; `levies` in comments), and the full record is the prose
in `optimisation/SOURCES.md`. A map can't link a box to a string reliably, and a
checker can't tell a missing source from a typo.

**Proposal: a source register in Python** (`optimisation/source_register.py`,
in line with the no-data-files rule). One entry per document or feed:

| field | example |
|---|---|
| key | `desnz_arup_2024_onshore` |
| title, publisher | "Cost of Electricity Report Update 2024 — Onshore Wind and Solar PV", DESNZ / Arup |
| version and date | ref 299867-00, Final, 14 Jul 2025 |
| kind | document · data feed · charging statement · register dataset · assumption |
| link | the public URL |
| local copy | path under `optimisation/data/` or the OneDrive source folder, if kept |
| for a feed: last fetched | from the cache or `substation_register/freshness.json` |
| price basis | real 2023 £, converted to 2025 £ by … |

A step names its source as `source=S.cite("desnz_arup_2024_onshore", "Table 3, p.6")`
— the register key plus the exact table, page or dataset id. A step with no
source must carry `grade="assumed"` and a one-line reason. The checker fails
the build otherwise.

On the page:

- every step's datasheet shows its source, table and page, link, date, and
  grade;
- one box per source at the bottom of the graph, with "Used by" listing every
  number that comes from it;
- a **Sources tab**: a table of every source — what it is, date, link, how
  many numbers use it, how many of those are assumed or stand-ins — sortable,
  with the data feeds' fetch dates and how old they are;
- the open cost gaps from `docs/COST_PLAN.md`, `DATA_GAPS.md` and `TODO.md` as
  badges on the boxes they affect, as the LCA map does with its gaps.

`SOURCES.md` stays the prose record; the checker holds each register entry to
having a row there.

What the cost side draws on, as far as I can see from the code (to be
completed by step A, which will find every one):

| Area | Sources |
|---|---|
| Wind, solar | DESNZ / Arup cost reports 2024 (onshore and solar; offshore) |
| Battery | Modo Energy cost model; NESO Future Energy Scenarios economics notes |
| Electrolyser | NESO hydrogen cost assumptions (AE / PEM); SOEC unsourced |
| Tank, fuel cell | proxies in `h2_capex.py` — flagged as the weakest numbers |
| Bought hydrogen | NESO hydrogen data portal levelised-cost datasets (green, blue); grey derived from gas and carbon prices (`h2_prices.py`) |
| Import price | Elexon market index price (feed); NESO balancing charge and national network charges (data portal); each local network company's 2026/27 charging statement and line loss factors; Ofgem / DESNZ levy rates |
| Connection | each local network company's 2026 connection price statement; NESO Section 14 annuity rules; the substation register (39 portal datasets) for route and voltage |
| Study settings | discount rate, value of lost load, connection circuits — assumed |

## 4. Steps

**A. Record every cost number where it is computed** (`T.step`, as the carbon
side does). Modules: `tech_costs.py`, `battery.py`, `h2_capex.py`,
`h2_prices.py` (price side), `connection_cost.py`, `network_charges.py`,
`duos_areas.py`, `ehv_charges.py`, `levies.py`, `grid_build.py` (wholesale
price), `dc_inputs.build_tech` (`coefficient.cost_*`, the bought price) and
`build_series` (each part of the import price), `dc_model` (value of lost load,
export credit). Roughly 100–150 steps. `T.step` returns its value unchanged
and costs nothing outside a recording, so **the model's answers must not move**:
check by snapshotting every `Tech` field and one solve before and after, equal
to 1e-12. Add the rule to `docs/LCA_STYLE.md` §1 (or a short cost note): any
pound figure that becomes an LP cost coefficient is recorded where it is made.

**B. The source register** (§3), and every cost step pointed at it. This is
where unsourced numbers get found and named — expect a list, which goes to
`DATA_GAPS.md`, not hidden.

**C. The builder** `scripts/build_cost_map.py`. Reuses the LCA map's readers
(LP terms on symbols, the trace recording, variant merging) — moved into a
shared `scripts/map_common.py` so the two maps can't drift — with the source
layer in place of Brightway and one solve of the reference run for the pounds
per box. Writes `optimisation_outputs/cost_map.json` and `cost_map.html`.
Refuses to write on any problem, as the LCA map does.

**D. The page.** The LCA map's template with pounds instead of carbon, the
import-price breakdown, the Sources tab, and a link across to the LCA map.

**E. The checker** `scripts/check_cost_map.py` + `tests/test_cost_map.py`:
- every cost coefficient on `Tech` and every cost term in `dc_model` is in the
  map, and nothing in the map is not;
- every step has a register source with a locator, or is graded assumed with a
  reason; every register entry is used and has a `SOURCES.md` row;
- the import-price parts add back to the series; the solved terms add back to
  the objective total;
- a fingerprint of the code and inputs, so a stale map is caught.

**F. Publish** as a private artifact, record it in memory beside the LCA map,
add a line to `TODO.md`.

## 5. Decisions for you

1. **Show pounds from a solved run, or only unit prices?** The LCA map shows
   unit coefficients, not a solved build. For cost I'd show both: the unit
   price on each box and what it came to in one reference run, because "which
   box is most of the bill" is the question a cost map answers. Which run —
   London 100 MW, cost-optimal, optimiser choosing the price list?
2. **Separate page, or a cost tab on the LCA map?** I'd make it a separate page
   sharing the builder and look: the LCA map is already 1,850 boxes, and the
   cost map should open fast.
3. **The source register in Python** (new file) rather than parsing
   `SOURCES.md`. Parsing prose would be fragile and couldn't catch a missing
   source.
4. **When to start.** Step A edits the same files the grid-connection sessions
   have open right now (`dc_inputs.py`, `network_charges.py`,
   `connection_cost.py`, `connection_options.py`, `levies.py` — uncommitted in
   this checkout). Either wait for that work to be committed, or start on the
   modules nobody is in (`tech_costs`, `battery`, `h2_capex`, `h2_prices`) and do
   the grid ones last.
