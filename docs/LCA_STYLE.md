# How an LCA is written here — the style sheet (22 Oct 2026)

Every life-cycle inventory in this study is a Python module in
`optimiser_lca/`, in the shape `optimiser_lca/common.py` defines, readable top
to bottom without opening a notebook, a spreadsheet or a data file. This sheet
says what that shape is, so a module can be checked against it. It is written
from the modules as they stand (`data_centre.py` and `h2_tank.py` are the
shortest clean examples; `upv.py` and `bess.py` the largest).

The rules in **bold** are the ones a test can hold (`tests/test_lca_style.py`,
`LCA_ASSURANCE_PLAN.md` Part 4). The rest are for the reader doing the review.

## 1. Where things live

| What | Where | Never |
|---|---|---|
| An inventory: processes, flows, activities, amounts, units, scale factors, the parameters that set them | `optimiser_lca/<one module per LCA>.py` | `dc_config.py`, a notebook, `optimisation/`, JSON, CSV, YAML, xlsx |
| Database names and activity codes | `optimiser_lca/registry.py`, once | string literals in a module or a test |
| The shape and the verbs (`Process`, `Flow`, `FG`, `Activity`, `Inventory`; `check`, `pin`, `resolve`, `show`, `write`) | `optimiser_lca/common.py` | re-implemented in a module |
| Study settings applied *after* scoring (project name, operating lives, PV geometry) | `dc_config.py` | anything that changes an exchange amount |
| Coefficients the LP reads, derived from scored activities | `optimisation/<asset>.py` → `tech_lca_coefficients.csv` | inventory rows |
| Source documents as evidence (a transcription, a workbook as shipped) | `optimisation/data/`, or `SOURCE_DOCS_DIR` on OneDrive | read by a module to build an activity |
| Scores and decompositions, cached | `optimisation_outputs/*_cache.json`, regenerated by `python optimisation/coefficients.py` | hand-edited; read by `optimiser_lca/` |
| The notebook `2.tech_lca_foreground.ipynb` | reads and shows; builds nothing | `Activity(`, `Database(`, `.write(` |

**A module in `optimiser_lca/` constructs its inventory from Python literals
and arithmetic on them. It does not open a file to get an amount.** The one
file read that exists is a check, not an input: `gb_grid.check_against_series()`
re-derives `MIX_2025` from the series CSV it was transcribed from (`grid.py`
uses `json` only to canonicalise the basis it hashes into `sources_id()`).
Any new file read or data-module import in the package needs a line in
`ALLOWED_IO` in `tests/test_lca_style.py` and a reason.

**A number in `optimisation/` that becomes an LP carbon coefficient is wrapped
in `T.step(...)` (`optimisation/trace.py`) where it is computed, with the steps
and activities it `uses`.** The LCA map is generated from those records
(28 Oct 2026), so it shows the expression, file and line that made each number.
`step` returns its value unchanged and costs nothing outside the map's build.
A step whose value is an activity's score says so with `scores=`, and the map's
build rescores it. A new coefficient with no step shows up as a build problem,
since the map cannot reach it.

## 2. The module, top to bottom

Every module has the same order, separated by the `# ===` rules:

1. **Docstring.** First line: *what — whose source, what design*. Then a
   `Source and scope` section with the full citation (authors, year, journal
   or report number, DOI, which tables or SI sheets), the functional unit in
   bold, the boundary (what is in; what is out and which way it errs), every
   substitution with what replaced what and why, and how the module was
   verified (reconciles to a printed total, reproduces a published figure,
   `validate.py`). Dated "since <date>" notes only where a reader of the
   numbers needs the date; the history is in git and `SOURCES.md`.
2. **Imports.** `from optimiser_lca import registry as R` and the names it
   uses from `common`. Nothing else from outside the standard library, except
   another `optimiser_lca` module it links into (`gb_grid` imports `grid`).
3. **Parameters.** Module-level constants, one family prefix per source
   (`UPV_`, `CSS_`, `CELL_`, `TX_LENG_`, `FC_`, `TANK_`), each **tagged on its
   line or in its block as `TRANSCRIBED`, `DERIVED` or `ASSUMED`** and, where
   transcribed, saying from where ("Smith Table 3", "Teffera Table 2").
   Derived values are written as the arithmetic, not the result
   (`UPV_PV_M2_PER_MWP = 1e6 / UPV_PV_W_PER_M2`, not `4914`).
4. **Scope dict**, where the module makes scope choices: `<FAMILY>_SCOPE = {
   topic: sentence }`, each sentence starting `INCLUDED`, `EXCLUDED` or
   `SUBSTITUTED`, with the direction of the error for exclusions. Every
   `EXCLUDED` entry is a row in the cut-off register
   (`optimiser_lca/exclusions.py`, once Part 1 of the assurance plan lands).
5. **`check()`**: the module's own reconciliations — a bill sums to the
   source's printed total within a stated tolerance, a ratio sits in a
   plausible band, a value another module reads agrees with this one
   (`stepup_transformers.check()` holds `CSS_TX_KG` to `bess.CSS_EXCLUDED`).
   Returns `"OK - ..."` or raises. `tests/test_optimiser_lca.py` calls it.
6. **`processes`** then **`flows`**: the two tables, §3.
7. **`activities`**: the list, §4.
8. **`inventory()`** returning `Inventory(name, database=R.<DB>, processes,
   flows, activities)`, and **`describe()`** where there is a design choice
   worth printing (which tank, which cell factory, what is excluded).

Nothing executes at import beyond building these literals and asserting a
configuration constant is valid (`h2_tank.TANK_DESIGN in TANK_DESIGNS`).

## 3. The two tables

```python
"concrete": Process(
    query="market for concrete 30-32MPa", pick=0,
    identity=("market for concrete, 30-32MPa", "RNA", "concrete, 30-32MPa"),
    why="the paper's own named process; North American market suits a Virginia build"),
```

- **Keys are `snake_case` and mean something** (`steel_chromium_188`, not
  `p7`). A key that mirrors an external identifier keeps that identifier's
  case: the grid fuels are the Carbon Intensity API's own names (`GAS`,
  `IMPORTS_FR`), which the series id hashes. **No key appears in both
  `processes` and `flows`** (`common.check()` refuses it; `resolve()` merges
  the tables).
- **Every `Process` carries `identity` and `query`.** The identity is
  `(name, location)` or `(name, location, reference product)`, the exact
  ecoinvent strings; the query is the search that found it and `pick` its
  rank. `unit=` only where the same name exists per kg and per unit.
- **`why` is required when the pick is not the source's own process name**
  (a proxy, a substitution, a regional choice, `pick > 0`), and says what the
  neighbours were and why not them. It is optional when the identity *is*
  the source's row.
- **Every `Flow` has `identity=(name, (compartment, ...))`**, the categories
  tuple pinned, with a `why` where the compartment was a choice (the two
  "Water" flows; Smith's rows named by substance only).
- A module that needs many near-identical entries uses a two-line helper
  (`_p(name, loc, product, why)`, `_f(name, categories, why)`) and still
  writes one entry per line. It does not paste a schema or loop over a
  table.

## 4. Activities

```python
Activity(
    code=R.H2_TANK,
    name="Hydrogen storage tank, steel vessel, per kg capacity (gandiglio_28bar)",
    reference_product="hydrogen storage capacity",
    unit="kilogram", location="GLO",
    comment="... what it is, whose table, the functional unit, what is left out ...",
    technosphere=[
        ("steel_chromium_188", TANK_STEEL_KG_PER_KG_H2, "kilogram", "Vessel steel — Gandiglio Table 5, 28 bar"),
        ("concrete_normal",    TANK_FOUNDATIONS["concrete_m3"], "cubic meter", "Pad, 0.5 m slab - ASSUMED"),
    ],
    biosphere=[],
)
```

- **One activity per source table**, named for what it is and whose
  (`"Data centre facility, hyperscale, Virginia (Zhang et al. 2025)"`), its
  **`code` from `registry`**, never a literal. Variants that differ only by a
  named parameter (the CN and DE cell factories) come from one small helper
  with those parameters as arguments; the helper is the only loop allowed.
- **Rows are the source's rows, as printed, one per line, aligned**:
  `(key, amount, unit, note)` — four fields, always. The amount is the
  printed figure or a named constant; a conversion the source did not print
  is written as arithmetic in the row (`2.80e5 / 3.6`) or as a parameter.
- **The activity's `comment` names its source table** (`"Zhang et al. 2025
  … Table 1 / supplementary Table S1"`, `"Usai et al. 2021 SI Table 1"`), so
  every row of it is located by its activity. **Every row carries a non-empty
  `note`** saying what the row is, as the source prints it. A row that is
  *not* from the activity's table says so at the start of its note: another
  locator (`"Z-PV-238 Table 50 — station building"` on the solar step-ups,
  `"Jasper SI liquid r17"` on the shared container) or `ADDED`, `ASSUMED`,
  `DERIVED`. The note is what the LCA map shows beside the number and what
  the source ledger (`LCA_ASSURANCE_PLAN.md` Part 2) parses; a row with no
  locator of its own belongs to its activity's table, and the ledger holds
  the module to that.
- **`scale` only with `scale_note`**, and the rows stay as printed; the
  correction is applied once at write time and `to_bw_dict` records "as
  printed" on every exchange. `production_amount` for a table published per
  batch (Smith's silica sand per 92,500 t); the map and the checker divide
  by it.
- **Rows knowingly dropped are commented at the foot of the activity they
  belong to**, with the printed amount and the reason (`# A14 sea leg 201
  t·km/m² — delivery to site, outside the boundary`). A dropped row with no
  foot comment is a row left out.
- Foreground links are `FG(R.<CODE>)`, with `database=` only across
  databases. Negative exchanges are allowed where the source's own factor
  must be unpicked (Voß's transport legs), with the note saying so.
- `comment` on the activity describes what the activity *now* contains. A
  comment that still describes a previous boundary is a defect (the facility
  activity's comment on 22 Oct says construction energy is excluded; its rows
  include it).

## 5. Clear and concise

- The module is the record. A reader with the module and the source should
  be able to put every number in one against the other without the notebook,
  `SOURCES.md` or git. `SOURCES.md` says *why this source*; the module says
  *what it contains*.
- No narrative of what the module used to do beyond one sentence where the
  change explains a number ("in since 21 Oct 2026; was excluded as a scope
  choice"). History lives in git and `SOURCES.md`.
- No commented-out code, no `TODO` in a module (TODO.md is the worklist), no
  duplicated constant (`CSS_TX_KG` is read from one place and *held* equal to
  another by `check()`, not written twice).
- Prose lines wrap at ~100 characters. Aligned row tables may run longer;
  **no line passes 140 characters** — a row that needs more has too much in
  its note.
- Names say what the thing is. A code that names the wrong author
  (`ae_hermesmann_1unit` is Gerloff's bill) is a defect to list, even if
  renaming it waits for a rebuild.

## 6. What a module must pass

| Check | Where | Needs Brightway |
|---|---|---|
| Units from `common.UNITS`; every row names a declared key or code; no duplicate codes; no key in both tables | `common.check()` via `test_inventory_is_well_formed` | no |
| The registry lists exactly the codes the module writes | `test_registry_lists_exactly_what_each_module_writes` | no |
| The module's own reconciliations | `<module>.check()` via `test_module_checks_pass` | no |
| Every identity resolves to exactly one activity and is still among its query's hits | `test_every_identity_resolves_and_is_findable` | yes |
| What is in Brightway is what the module says | `test_written_database_matches_the_module` | yes |
| The structure rules in bold above | `tests/test_lca_style.py` (Part 4 of the assurance plan) | no |
| Every row says where it came from; every source row has a disposition | `tests/test_sources.py` (Part 2) | no |

## 7. Review checklist (one module at a time)

- [ ] Docstring: what, whose, functional unit, boundary with directions, substitutions, verification. Nothing a reader of the numbers does not need.
- [ ] Every constant graded and, where transcribed, located.
- [ ] Scope dict present if the module makes scope choices; every `EXCLUDED` has a register row.
- [ ] `check()` reconciles to at least one printed total or published figure.
- [ ] Every `Process` has identity and query; `why` wherever the pick is a choice.
- [ ] Every `Flow` pinned with its compartment.
- [ ] One activity per source table; code from the registry; rows as printed; four-field tuples; locator-first notes.
- [ ] Dropped rows commented at the foot.
- [ ] Activity comments describe the activity as it is today.
- [ ] No file reads, no data files, no notebook dependence, no duplicated constants, no history narrative.
- [ ] `python -m optimiser_lca.build --check` passes; the module reads cleanly top to bottom.
